# 더스티치 OSMU 워크벤치

㈜더스티치 / 한복 새활용 브랜드 **더봄봄**을 위한 원소스 멀티유즈(One Source Multi Use) 콘텐츠 엔진.
담당자 메모와 현장 사진 한 벌에서 **네이버 블로그 · 인스타그램 · X · 쇼츠** 4개 채널 콘텐츠를 한 번에 만들고,
각 채널의 실제 레이아웃으로 미리 본 뒤 네이버에 반자동 게시합니다.

기존 `OSMU_admin`(Streamlit + Supabase + 폴링 워커)과 `OSMU_web`(Next.js 워크벤치)을
**하나의 Flet 데스크톱 앱 + 로컬 SQLite**로 통합한 것입니다. (중간 단계였던 Streamlit UI는 제거됐습니다.)

---

## 빠른 시작

```bash
python -m venv .venv
.venv\Scripts\activate             # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
playwright install chromium          # 네이버 게시 자동화용 (선택)

python flet_app/main.py
```

Windows용 .exe는 GitHub Actions(`.github/workflows/flet-windows-build.yml`)가 빌드합니다.

첫 실행 시 `data/osmu.db`가 만들어지고, `company_info/`에서 정리한 브랜드 킷이 자동으로 채워집니다.
그다음 **⚙️ 설정 → LLM 벤더**에서 API 키를 하나 이상 등록하고 [기본 생성 모델]을 지정하면 바로 사용할 수 있습니다.

`.env`는 전부 선택 사항입니다 (`.env.example` 참고).

## 왜 3-tier를 접었나

원래 구조는 Vercel(Next.js) → Supabase(큐/스토리지) → Streamlit(워커) 3계층이었고,
그 이유는 단 하나 **Vercel 서버리스 함수의 10초 타임아웃**이었습니다.
크롤링 + 비전 분석 + 수천 자 생성은 30초를 훌쩍 넘기니, 프론트는 큐에 INSERT만 하고
별도 워커가 Supabase를 폴링해 처리하고, 프론트는 Realtime으로 결과를 받는 구조였습니다.

한 프로세스로 합치면 우회할 타임아웃 자체가 없어집니다. 그래서 함께 사라진 것들:

| 사라진 것 | 이유 |
|---|---|
| Supabase Postgres | 생산자와 소비자가 같은 프로세스인 큐는 순수 오버헤드. SQLite 파일 하나로 충분 |
| `worker_runner.py` 폴링 루프 | 생성이 앱 프로세스 안 백그라운드 스레드에서 동기 실행됨 |
| Supabase Realtime 구독 | 같은 프로세스라 그냥 리턴값 |
| service_role 키 / RLS 정책 | 브라우저에 노출될 클라이언트가 없음 |
| 30일 TTL cron + Edge Function | 무료 티어 500MB/1GB 한도를 우회하려던 장치. 로컬 디스크엔 한도가 없음 |

## 사진 분석 토큰 최소화

사진 분석은 이 파이프라인에서 토큰을 가장 많이 먹던 지점입니다.
기존에는 **사진 1장당 1회 호출**로, 1024px 이미지와 담당자 메모가 들어간 ~350토큰짜리 지시문을
매번 같이 보냈고, 같은 제품 컷을 열 번 써도 열 번 다시 분석했습니다.

다섯 개 층으로 줄였습니다 (영향이 큰 순서):

**1. 캡션 캐시 (`vision_cache` 테이블)**
사진 *내용*의 sha256으로 캐싱합니다. 같은 컷을 다른 이름으로 다시 올려도 같은 해시라
분석은 평생 한 번, 재사용은 **토큰 0**입니다. 더봄봄처럼 제품 스튜디오 컷을 계속 재사용하는
브랜드에서 이게 제일 큽니다.

**2. 메모와 분리된 프롬프트**
기존 프롬프트는 "이 사진을 설명하고, *이 글의 어디에* 넣을지도 판단하라"고 물었습니다.
그래서 캡션이 글마다 달라져 애초에 캐시가 불가능했습니다.
지금은 비전 호출에 "보이는 것"만 묻고, 배치 판단은 어차피 메모·기사·전체 캡션을 다 가진
텍스트 호출이 합니다. 더 싸면서 역할 분담도 더 맞습니다.

**3. 벤더별 최소 과금 해상도**
각 벤더는 이미지를 면적으로 과금하되 하한이 있습니다. `economy` 프리셋은 딱 그 하한까지만 축소합니다.

| 벤더 | 절약(384px) | 균형(768px) | 고화질(1024px) | 축소 없이 3024×4032 |
|---|---:|---:|---:|---:|
| Gemini | **258** | 258 | 1,032 | 6,192 |
| OpenAI (`detail=low`) | **85** | 85 | 85 | 85 |
| Anthropic | **196** | 786 | 1,398 | 16,257 |

**4. 배치 호출** — 미캐시 사진을 최대 6장씩 묶어 한 번에 보냅니다. 지시 프롬프트를 N번이 아니라 1번만 냅니다.

**5. 출력 상한** — 캡션 1장당 40~45토큰으로 `max_output_tokens`를 걸고, 프롬프트에도 글자 수를 명시합니다.

여기에 더해 업로드 시점에 모든 사진을 1280px JPEG로 정규화해 저장하므로(`core/storage.py`),
폰 원본 대비 실제 절감폭은 위 표보다 더 큽니다.

⚙️ 설정 → 사용량 탭에서 **실제 usage 값**(프로바이더 응답에 실려 온 값)과 절감률을 확인할 수 있습니다.
급하면 [이미지 분석 사용] 토글을 꺼서 비전 호출을 0으로 만들 수도 있습니다.

## 컴플라이언스: 의료법이 아니라 그린워싱

`OSMU_admin`의 가드레일은 **의료법·표시광고법** 기준이었습니다 (원래 헬스케어 고객용이었기 때문).
더스티치는 새활용 제품과 환경 교육을 팝니다. 실제 법적 리스크는

- 「환경기술 및 환경산업 지원법」 환경성 표시·광고 관리제도
- 「표시·광고의 공정화에 관한 법률」

쪽이고, 전형적인 위반은 "암을 고친다"가 아니라 **그린워싱**입니다 —
포괄적 환경성 주장("100% 친환경"), 근거 없는 정량 효과("탄소 3kg 절감"),
보유하지 않은 인증의 암시. 가드레일을 이 기준으로 다시 썼습니다 (`ai_workers/guardrail.py`).

2단 방어:

1. **결정론적 치환** — 브랜드 킷의 금기어 사전은 LLM이 무엇을 쓰든 100% 치환됩니다.
   치환어는 **원래 표현과 같은 품사·활용형**으로 골랐습니다. 한국어는 조사가 뒤에 붙어서,
   관형형을 명사구로 바꾸면 "국내 최초로" → "국내에서도 보기 드문**로**" 같은 비문이 나옵니다.
   긴 항목이 짧은 항목보다 먼저 매칭되도록 길이 내림차순으로 처리합니다.

   ```
   입력: 저희 제품은 100% 친환경이며 국내 최초로 무독성 소재를 사용한 최고급 굿즈입니다.
   출력: 저희 제품은 친환경적이며 국내에서도 보기 드물게 유해물질 저감 소재를 사용한 고급 굿즈입니다.
   ```

2. **LLM 감사** — 사전에 없는 새로운 과장 표현을 잡아내고, 점수 + 지적 사항 + **표현 단위 교정안**
   (`문제 표현 → 교정 표현`)을 반환합니다. 글 전체를 다시 쓰게 하지 않으므로 응답이 짧아 잘릴 일이 없고,
   지적하지 않은 문장이 몰래 바뀌지도 않습니다. 교정은 코드가 결정론적으로 적용합니다.
   **감사가 실패하면(응답 잘림·형식 오류·API 오류) '통과'가 아니라 '검수 미완료'로 표시**합니다 —
   예전에는 이 경우 100점 통과로 처리되어, 긴 글일수록 검수 없이 나갈 수 있었습니다.
   인스타 캡션과 X 스레드도 각자 브랜드 주장을 하는 별개 텍스트이므로 같은 감사를 거칩니다.
   단 X는 트윗 하나씩이 아니라 **스레드 전체를 한 번에** 감사합니다 —
   감사 시스템 프롬프트가 ~500토큰이라, 5개짜리 스레드를 낱개로 돌리면 300토큰짜리 내용을 보려고
   2,500토큰짜리 지시문을 내는 셈이고, 스레드 맥락 없이 트윗 하나만 본 판단이 더 나을 이유도 없습니다.
   구분자 구조가 깨져 돌아오면 결정론적 치환만 적용하고 원본 스레드를 유지합니다
   (금기어가 살아남지 않는다는 보장은 어느 경로에서든 유지됩니다).

## 브랜드 킷

`company_info/`의 회사 문서에서 뽑아 첫 실행 시 자동으로 채워집니다 (`core/brand_seed.py`).
빈 칸에서 시작하지 않으므로 **첫 초안부터** 제품명·가격대·인증·화법을 알고 씁니다.

- 핵심 팩트 15개 (새활용제품인증 4건, 2023·2024 새활용산업 육성지원사업 선정, 기부 한복 200벌 등)
- 용어집 14개 (더봄봄 / 새활용 / 행복인형 / 향낭 / 짱리본핀 / 금빛 라이프 굿즈 …)
- SEO 키워드 10개 · 금기어 사전 27쌍 · 우수 포스팅 샘플 1개
- 페르소나 & 톤앤매너 ("환경 이야기를 첫 문단에 꺼내지 않는다", "예뻐서 골랐는데 알고 보니 의미까지 있더라"는 순서)
- 한복 오방색 팔레트 (자주 #A6224B / 쪽빛 #2B4C8C / 금박 #C9A227 / 옥색 #86C1B3 / 한지 #FBF7F2)

브랜드 킷 데이터는 유사도 검색(RAG)이 아니라 **매번 전체 주입**합니다.
용어집 14개는 전부 넣어도 ~600토큰이고, 검색이 한 번 빗나가 '더봄봄'을 '더 봄봄'으로 쓴 초안이
나오는 쪽이 훨씬 비쌉니다.

채널 정보는 `company_info/sns_info.txt` 기준: 블로그 `migoi1`, 인스타 `@thestitch_artplay`, `thestitchstore.co.kr`.

## 채널 시뮬레이터

발행 후에야 보이는 문제를 발행 전에 잡는 것이 목적입니다.

- **네이버 블로그** — 880px PC ↔ 390px 모바일, 16px/1.8 줄간격, 마루부리 계열 본문.
  `[IMAGE:]` 태그 자리에 사진이 인라인으로 들어가고, 태그되지 않은 사진은 글 끝 갤러리로 경고와 함께 붙습니다.
- **인스타그램** — 4:5 캐러셀, **125자 '더보기' 절단선을 실제로 그려서** 어느 단어가 접히는지 보여줍니다. 10장 초과 시 경고.
- **X** — 140자 타래 자동 분할(문장 경계 우선), 사진 1~4장에 따라 달라지는 그리드 4종, 5장째부터 잘린다는 경고.
- **쇼츠** — 9:16 프레임에 우측 버튼 클러스터 / 하단 캡션 데드존과 SAFE AREA를 겹쳐 그리고,
  컷별 자막이 20자를 넘으면 경고합니다.

## 네이버 반자동 게시

네이버는 스마트에디터에 봇이 글을 넣는 것을 차단하므로, 의도적으로 **반자동**입니다.

1. [로그인 세션 저장] — Chrome 창이 열리고 직접 로그인하면 세션이 `data/naver_state.json`에 저장됩니다.
   (이 쿠키만은 DB에 넣지 않습니다. 살아 있는 발행 계정 접근 권한이라, 지우기 쉬운 파일 하나로 둡니다.)
2. [지금 게시] — 백그라운드 스레드가 Chrome을 띄워 제목을 입력하고, 본문/사진을 **문서 순서대로 하나씩**
   붙여 넣습니다. 마지막 [발행] 버튼은 담당자가 직접 누릅니다. 게시 창은 담당자가 닫을 때까지 열려 있고,
   자동으로 넣지 못한 사진·제목이 있으면 게시 화면에 경고로 표시됩니다. 같은 글을 두 번 누르거나
   여러 글을 동시에 게시해도 클립보드가 섞이지 않도록 붙여넣기 단계는 한 번에 하나씩만 진행됩니다.
3. [발행] 팝업의 태그 입력란은 자동화가 불가능하므로, 생성된 해시태그를 화면에서 복사해 붙여넣습니다.

절대 headless로 돌리지 마세요. 봇 탐지와 최종 발행 클릭 모두 사람이 앞에 있다고 가정합니다.

### 파이프라인 단계 순서

1. 사진 캡션 (캐시·배치)
2. 본문 초안 — 메모 + 기사 + 캡션을 모두 보는 유일한 호출
3. 컴플라이언스 가드레일 — 글을 다시 쓰므로 밀도 검사보다 먼저
4. SEO 키워드 밀도 — 2단계에서 *지시만* 한 것을 실제로 검증
5. 금기어 사전 재적용 — 3·4단계는 새 LLM 출력이므로 결정론적 치환을 한 번 더
6. 이미지 태그 백스톱 — 첨부 사진이 조용히 사라지지 않도록
7. 인스타 / X / 쇼츠 / 네이버 태그 — 네 채널을 **병렬로** 생성, best-effort, 실패해도 본문은 살림

2단계 직후 초안을 먼저 저장하므로, 이후 단계에서 API 오류가 나도 비용을 낸 초안은 편집기에 남습니다.
같은 글에 생성·수정이 동시에 두 번 돌지 않도록 막고, 앱이 생성 도중 꺼졌다면 다음 실행 때 '실패'로
표시해 다시 생성할 수 있게 합니다.

## 데이터와 백업

전부 `data/` 안에 있습니다: `osmu.db`(SQLite), `assets/`(사진), `.master_key`(API 키 암호화 키, 0600),
`naver_state.json`(네이버 세션). 이 디렉터리만 백업하면 됩니다.

`data/`를 클라우드에 동기화한다면 마스터 키는 밖으로 빼세요 (앱은 시작할 때 프로젝트 루트의 `.env`를 읽습니다.
마스터 키를 찾지 못했는데 이미 암호화된 키가 저장돼 있으면, 새 키를 만들어 기존 키를 못 쓰게 만드는 대신 오류를 냅니다):

```bash
python -c "import os,base64;print(base64.b64encode(os.urandom(32)).decode())"
# → .env 의 ENCRYPTION_MASTER_KEY_BASE64 에 넣고 data/.master_key 삭제
```
